`GROUP_ID` у одиночной компании не доказывает холдинг или самостоятельность: другие участники могут отсутствовать в выгрузке. `NEGATIVEMARK` по словарю — наличие ключевого собственника, не негативный стоп-фактор.

Отчёт `dataset-report.json` и агрегаты сайта теперь создаются одним скриптом. Все показатели компаний считаются по одной очищенной базе; пропущенный продукт остаётся неизвестным. Исходные CSV и реальные ID в Git не попадают.

## Что уточнить в аналитике перед защитой

- Исправить загрузчик архива: реальные имена и кодировки CSV, отсутствие `Uid_product` и `REVENUE_GROUP` в v2, конфликтующие ID. Работа с Excel допустима; для 1 380 585 платёжных строк нужен Power Query / модель данных вместо загрузки целиком на лист.
- Слайд 8 обозначить как предложение для следующего этапа. Проверить формулу выбора продукта: сейчас текст и скрипт архива расходятся при частичном кредитном покрытии группы.
- Числа 8 158 / 2 036 / 435 / 2 389 на ячейку арифметически верны для заданных условных баз, α=5%, мощности 80% и двух независимых пропорций. Они ещё не являются готовым дизайном пилота.
- Г3: при рандомизации холдинга и метрике по компаниям нужны кластерный расчёт мощности и кластерный анализ. Основной результат считать по заранее заданной допустимой аудитории (ITT); клик сотрудника использовать как этап воронки, а не формировать по нему основную выборку после воздействия.
- Г2 с тремя ячейками и вариант 2×2 требуют заранее выбранных сравнений, поправок и единиц анализа. Универсальное правило «достаточно 2n на четыре ячейки» применять нельзя.
- Из 4 528 кандидатов С1 получается максимум 2 264 группы на ячейку до исключений. Для условного роста 5% → 6% нужно 8 158 на ячейку: доступная выгрузка такого объёма не даёт. Численность всей банковской базы неизвестна.
